# CRD Schema Validation at Server Startup

## Background

Velero server can currently start against CRDs from any Velero version — for example v1.15.x CRDs installed alongside a v1.16.x server. The existing startup check, `veleroResourcesExist()`, only verifies that the Velero CRDs exist and expose the expected API group/version. It does not verify that the installed CRD's schema actually contains the fields the running server's Go API types expect.

When CRDs are stale relative to the server, this produces silent failures, confusing runtime errors far from their root cause, and no proactive signal telling the user to run `velero install --crds-only` (added in #9132) to bring the CRDs up to date.

Issue #9260 requests a startup-time compatibility check so that mismatches are caught immediately, with a clear message, instead of surfacing later as an unrelated-looking bug.

## Goals

- Validate at server startup that installed CRD schemas contain the top-level `spec`/`status` fields the server's Go API types expect (nested/sub-object schema shape is out of scope — see Design > Expected schema derivation).
- Fail fast with an actionable error message (naming the missing fields and suggesting `velero install --crds-only`) when validation is configured to be strict — without crash-looping the container, so the pod stays available for in-place remediation (see Design > Self-resolution guidance).
- Default to warn-only behavior so existing deployments are not broken by upgrading to a server with this check — including not adding a mandatory startup delay: see Design > Validation flow for why `warn` mode runs the check asynchronously rather than blocking `run()` on the same shared timeout `strict` mode uses.

## Non Goals

- Enforcing CRD compatibility via a `ValidatingAdmissionWebhook` (considered, see Alternatives Considered).
- Detecting/handling patch-version-only CRD differences specially; the schema-property comparison already tolerates patch releases that changed no fields, so no separate version-matching logic is needed.
- Introducing a stored, hand-maintained schema/version map that must be kept in sync manually; the expected schema is derived from the Go API types at runtime instead.
- Detecting the CRD-ahead-of-server case, i.e. the installed CRD schema having *more* fields than the server's Go API types recognize (raised in [review discussion](https://github.com/velero-io/velero/pull/10010#discussion_r3824046811)). This check simply doesn't flag it — extra CRD fields the server's Go type doesn't have are, by design, absent from `checkMissing`'s output (see Installed schema extraction and comparison), since the check's job is "does the CRD have what the server needs," not "does the server have everything the CRD offers." That's a narrower claim than "newer CRDs are generally compatible with older servers": a field the server doesn't know about is dropped when it unmarshals the object into its (older) typed Go struct, and *most* of Velero's write paths persist changes via a JSON merge patch computed between two typed objects (`kube.PatchResource`, `pkg/util/kube/client.go:28`, via `client.MergeFrom`) rather than a full-object PUT — for those, the unrecognized field's *value* is at least left untouched server-side rather than erased. But this is not universal, and shouldn't be stated as if it were: `setDefaultBackupLocation` (`pkg/cmd/server/server.go:405-430`, run once at server startup when `--default-backup-storage-location` is set and the target BSL isn't already flagged default) does a typed `Get` followed by a full-object typed `client.Update(ctx, backupLocation)` — not a merge patch — so an unrecognized field on that specific `BackupStorageLocation` *would* be silently dropped the one time this path fires. The value-preservation claim holds for ordinary reconcile-loop writes (backed by `kube.PatchResource`'s widespread use across controllers), not as a blanket guarantee across every write path in the codebase; a full audit of every CR-writing call site is out of scope for this design, but this one counterexample is confirmed, not hypothetical. Separately, even where merge-patch preservation *does* apply, it says nothing about whether the newer CRD version also tightened *validation* (a new `required` constraint, a stricter pattern/enum, a CEL rule) in a way the stored value doesn't satisfy — Kubernetes structural-schema validation runs against the *whole* object after a merge patch is applied, not just the patch body, so a previously-valid stored value becoming non-conformant under a newly-tightened rule would get an unrelated field's merge patch rejected at admission too. This is a real gap, distinct from the missing-field case this design addresses, and deserves its own `warn`/`strict`/`skip` axis rather than being folded into `--crd-schema-check`. Deferred as a follow-up design; in the meantime, `--crd-schema-check=warn` (the default) already surfaces the common companion case — a server upgraded ahead of stale CRDs — with no extra action required.

## Design

### CRD version identification approaches considered

| Approach | Verdict |
|---|---|
| `controller-gen.kubebuilder.io/version` annotation | Insufficient — CRD schema can change without a controller-gen version bump |
| `app.kubernetes.io/version` label on CRDs | Rejected — forces a CRD reapply on every patch release even when the schema is unchanged |
| Schema hash validation | Rejected — a hash mismatch says *that* something differs, not *what*, and is brittle to non-semantic YAML differences |
| Static resource-version compatibility matrix in server code | Rejected — another hand-maintained artifact that drifts from the real API types |
| **Schema property validation (chosen)** | Reflects on the Go API types for expected top-level JSON field names, and compares them against the installed CRD's `openAPIV3Schema.properties`. Directly answers "does the CRD have what the server needs," and missing fields are named in the resulting message. |

### Expected schema derivation

A new file `pkg/cmd/server/crd_check.go` builds the expected schema for each Velero CRD kind from the existing type registries `velerov1api.CustomResources()` and `velerov2alpha1api.CustomResources()` (`pkg/apis/velero/{v1,v2alpha1}/register.go`), rather than a hand-maintained map:

```go
type crdSchemaExpectation struct {
	crdName            string
	specType           reflect.Type
	statusType         reflect.Type
	apiGroupVersion    string
	storedVersionLabel string
}

func expectedCRDSchemas() []crdSchemaExpectation
```

Despite its name, `apiGroupVersion` holds only the bare version string (e.g. `"v1"`, from `SchemeGroupVersion.Version` — the `Version` field alone, not `Group`+`Version` combined), matching a CRD's `spec.versions[].name` directly, which is also always bare. Called out explicitly because the field's name reads as if it might hold a combined `"velero.io/v1"`-style string, which it never does and shouldn't be made to.

For each registered kind, the `Spec`/`Status` field types are read off the registered item type via reflection. `jsonFieldNames(t reflect.Type)` walks a struct's fields and collects the top-level `json` tag names, skipping untagged and `json:"-"` fields. It follows `encoding/json`'s own promotion rule for anonymous/embedded fields: an embedded field with **no** JSON tag is flattened into the parent (its own fields collected in place of a name for the embedded field itself), while an embedded field with an **explicit** tag name (e.g. an embedded `Metadata` tagged `json:"metadata,omitempty"`) is treated as an ordinary named field and is not flattened.

**Known gap in the reference implementation:** real `encoding/json` does not skip an untagged exported field — it includes it under its Go field name — and it does the same for a tag with an empty name portion (e.g. `json:",omitempty"`), falling back to the Go field name rather than dropping the field (verified empirically against the stdlib, not assumed). It also skips unexported fields entirely (regardless of tag), which the reference implementation's loop does not explicitly check for either. The reference implementation's `jsonFieldNames` (`pkg/cmd/server/crd_check.go` in #9910) currently doesn't handle the untagged, empty-name-tag, or unexported-field cases the way `encoding/json` does, so such a field would never enter the expected set (or, for an unexported+tagged field, could wrongly enter it despite never actually being marshaled) — either way a real mismatch involving it would go undetected or falsely flagged. Checked against every current Velero v1/v2alpha1 `Spec`/`Status` field: none are untagged, empty-name-tagged, or unexported-with-a-tag today, so this is a latent gap, not a live false negative/positive — worth adding focused tests for (untagged fields, unexported fields, invalid tags, duplicate JSON names, anonymous interfaces) and fixing in the reference implementation before it bites a future field addition, but not a blocker for this design.

### Installed schema extraction and comparison

`schemaPropertyNames(schema *apiextv1.JSONSchemaProps, path string) (sets.Set[string], bool)` walks the CRD's `openAPIV3Schema` down a dotted path (`"spec"` or `"status"`) and returns the property names defined at that node, plus a boolean distinguishing "path could not be traversed" (`false` — e.g. the CRD's schema has no `spec`/`status` section at all) from "the node exists but legitimately declares no properties" (`true`, empty set). This distinction is what makes the check fail closed: `checkMissing` treats an untraversable path as an empty installed-field set, so every expected field is reported missing, instead of silently treating an absent section as "nothing to check" (an earlier version of the check returned `nil` for both cases, which let a CRD with a missing `spec`/`status` section pass validation entirely).

`checkMissing(goType, schema, section, crdName)` diffs the expected (Go) field set against the installed (CRD) field set and returns only fields the **server expects but the CRD does not have** — i.e. an outdated CRD. Fields present in the CRD but not in the current Go type are intentionally not flagged; that's outside this check's scope (does the CRD have what the server needs), not a claim that a CRD newer than the server is generally compatible with it — see the CRD-ahead-of-server caveats in Non Goals.

### Validation flow

`(s *server) validateCRDSchemas() error`:

1. Returns immediately, logging at info level, if `s.config.CRDSchemaCheck.String() == "skip"` — `CRDSchemaCheck` is a `*flag.Enum` (see Configuration below), not a plain string, so the comparison goes through its `String()` accessor rather than comparing the pointer directly.
2. Builds an `apiextclient.Interface` from the server's existing kube client config — no new RBAC is required, since Velero's server already needs `get` on CRDs for other startup checks. This step happens synchronously in *either* mode, before the `warn`/`strict` branch in step 3 below — a genuine client-construction failure (e.g. a malformed kube client config) is a setup error, not a validation result, and propagates as an immediate startup error in `warn` mode exactly as it does in `strict` mode; only the CRD-checking work itself (step 3) is what runs asynchronously in `warn` mode.
3. In `strict` mode, delegates to `runCRDSchemaValidation(ctx, client, expectations, mode, logger)` synchronously, passing a single `context.WithTimeout(s.ctx, s.config.ResourceTimeout)` shared across every CRD `Get` in the pass — the same configurable timeout already used elsewhere in this file (`pkg/cmd/server/server.go`) — rather than one timeout per `Get`. With 13 registered CRD kinds today, a *per-Get* timeout would let a fully unreachable API server stall startup for up to 13×`ResourceTimeout` (10 minutes by default → over 2 hours) checked sequentially; one shared deadline caps the whole pass at `ResourceTimeout` regardless of CRD count. A `Get` that doesn't complete before the shared deadline (or before `s.ctx` itself is cancelled) is recorded the same fail-closed way as any other fetch error (below); every remaining CRD that the deadline firing prevented from being attempted at all also gets its own **validation-unavailable** entry (naming the CRD and "validation not attempted — startup deadline reached") rather than being silently omitted, so `warn`-mode output doesn't understate how much went unchecked.

   In `warn` mode, the *same* `runCRDSchemaValidation` call instead runs in a background goroutine, logging its result whenever it completes rather than blocking `run()` at all. This is deliberate, not an oversight: `warn` mode's entire premise is "advisory, never affects startup" (see Goals), so gating even `warn` mode's startup on the same `ResourceTimeout` deadline used for `strict` mode — up to 10 minutes by default — would itself be a real, mandatory regression for every default-configuration deployment upgrading to this check, silently contradicting that promise. Running it asynchronously keeps `warn` mode's startup-time cost at effectively zero, matching today's behavior, while still surfacing the same message once available. For each expected CRD (in either mode):

   - `Get`s the CRD by name (`<plural>.velero.io`). A `NotFound` result (`apierrors.IsNotFound(err)`) means the CRD is missing outright — recorded as a **missing-field-style** entry (`<crd>: CRD not found`) recommending `velero install --crds-only`, the same remediation as a real field mismatch, since a missing CRD *is* an outdated-CRD condition. Any other fetch error (timeout, RBAC `Forbidden`, network failure) is logged as a warning and recorded as a distinct **validation-unavailable** entry instead — these call for different remediation (checking RBAC/connectivity, not reinstalling CRDs) from a genuine schema mismatch (see below). **In practice this `NotFound` path rarely fires today**: `run()`'s existing, unmodified `veleroResourcesExist()` check (`server.go:471`, called before `validateCRDSchemas` — see Integration point) already discovers every expected Kind's API group/version via the discovery client and exits the process the old way (`cmd.CheckError` → `os.Exit(1)`) if any is missing entirely — so a wholesale-missing CRD is caught, and crashes the container, before `validateCRDSchemas` ever runs. The `NotFound` case described here only fires for the narrower window this design doesn't otherwise cover: a CRD present at discovery time but deleted before this `Get` runs, or a similar race — not the common "CRD was never installed" scenario. Unifying `veleroResourcesExist()`'s missing-CRD detection into this same framework, so a wholesale-missing CRD *also* gets `strict`-mode's blocking-not-crashing treatment instead of the older crash path, is a real improvement but a meaningfully bigger change than this design's current scope (see Open Issues).
   - Locates the schema for the CRD version matching `apiGroupVersion`. A CRD that exists but has no schema for that version is also a **missing-field-style** entry, not validation-unavailable — the CRD was successfully fetched, it's just missing the version the server needs, which `velero install --crds-only` directly fixes.
   - Runs `checkMissing` against both `spec` and `status`; a real mismatch here is recorded as a missing-field entry.
   - Aggregates every entry into one message, but keeps the two kinds visibly distinct: missing-field-style entries (missing CRD, missing version schema, or a specific missing field) are named `<crd>: <reason>` or `<crd>: <section>.<field>` and suggest `velero install --crds-only`; validation-unavailable entries (fetch error, timeout, or a CRD skipped due to the shared deadline) are named `<crd>: <reason>` and instead suggest checking the ServiceAccount's `get` RBAC on `customresourcedefinitions` and API server connectivity — recommending `velero install --crds-only` for an RBAC or connectivity failure would send the operator to fix the wrong thing.
4. In `strict` mode, controller startup is blocked and the aggregated message is logged at error level whenever *any* entry exists — missing-field-style or validation-unavailable alike, including a pure RBAC/connectivity failure with zero actual schema mismatches, since "couldn't verify compatibility" is exactly as unsafe to proceed past as "verified incompatible" — see Design > Self-resolution guidance below for exactly what "blocked" means (the process no longer exits, and the shared deadline from step 3 bounds how long `strict` mode can wait before reaching this point). In `warn` mode (default), the same message is logged at error level whenever the background goroutine from step 3 finishes — which may be after `runControllers()` has already started, since nothing in `warn` mode waits for it.

**Scope note:** the shared-timeout and `strict`-synchronous/`warn`-asynchronous split described in steps 3-4 above are, like Self-resolution guidance below, proposed refinements beyond the reference implementation (#9910) — its actual `runCRDSchemaValidation` runs synchronously with no timeout at all, identically in both `warn` and `strict` mode. That's exactly the mandatory-startup-delay-in-`warn`-mode problem this scope note's fix addresses; it just hasn't landed in #9910 yet either. The `1ef22a132` reference commit is the closest existing thing to test against, not the finished target.

### Integration point

In `pkg/cmd/server/server.go`, `(s *server) run()` calls `s.validateCRDSchemas()` immediately after the existing `veleroResourcesExist()` check succeeds, keeping the two CRD-related startup checks (existence, then schema) colocated. The reference implementation (#9910, pre-dating the self-resolution amendment below) treats any error the same way:

```go
if err := s.validateCRDSchemas(); err != nil {
	return err
}
```

The self-resolution amendment changes this call site's contract: a `strict`-mode schema mismatch is no longer reported by returning an error here — `validateCRDSchemas` instead blocks internally (see below) and this line is never reached for that case. In `warn` mode, `validateCRDSchemas` returns essentially immediately (per Validation flow above, the actual check runs in a background goroutine), so this line was never a meaningful gate in that mode to begin with, before or after the amendment. The snippet above still applies as-is to a genuine setup failure (e.g. the apiextensions client itself fails to construct) — that remains a real, immediate startup error distinct from "the CRDs don't match," which is exactly the validation-unavailable-vs-missing-field distinction drawn in Validation flow above.

### Configuration

A new server flag, `--crd-schema-check`, is added to `pkg/cmd/server/config/config.go`:

- `Config.CRDSchemaCheck` is a `*flag.Enum` (Velero's existing `pflag.Value`-implementing enum flag type in `pkg/cmd/util/flag`), constructed via `flag.NewEnum("warn", "warn", "strict", "skip")` — default `"warn"`, restricted to those three values.
- Valid values: `warn` (log an error-level message but continue starting — default, preserves current behavior for existing deployments), `strict` (block controller startup on mismatch and report the pod not-ready until the CRDs are fixed and the pod is restarted — see Design > Self-resolution guidance; the process itself no longer exits *for a CRD that exists but has a stale/incompatible schema*. A CRD that's missing entirely is still caught earlier, by the existing unmodified `veleroResourcesExist()` check, which still exits the process the old way regardless of `--crd-schema-check` — see the caveat in Validation flow and the related Open Issues entry), `skip` (perform no check).
- Using `flag.Enum` instead of a plain string means an invalid value (e.g. `--crd-schema-check=bogus`) is rejected by pflag at flag-parse time with a clear error, instead of silently falling through the mode switch inside `validateCRDSchemas`.
- A named-mode flag was chosen over a bool so that `skip` remains available independently of `strict`/`warn` — for example during a rolling upgrade window where a mismatch is expected and should not even be logged.

### Self-resolution guidance on `strict`-mode failure

`cmd.CheckError(s.run())` (`pkg/cmd/errors.go`) calls `os.Exit(1)` on any error `run()` returns, including a `strict`-mode validation failure. That crashes the container, and the Deployment restarts it into CrashLoopBackOff — the opposite of helpful, since it removes the one thing (a running container) an operator could use to fix the problem in place with `kubectl exec`.

Proposed change: on a `strict`-mode failure, `validateCRDSchemas` no longer returns an error up through `run()` (avoiding the `os.Exit(1)` path). Instead:

1. The aggregated missing-field message is logged at error level, same as `warn` mode, plus two concrete remediation commands (below).
2. The server sets an internal not-ready flag (an `atomic.Bool`, read by the `/readyz` handler and written here and at controller-startup completion — see point 3) and blocks on `<-s.ctx.Done()` instead of proceeding to `runControllers()` — the process stays alive and the container stays `Running`, so it remains exec-able, but no controller logic runs against schema-incompatible CRDs. **This block must not silently return `nil` when unblocked.** `s.ctx` is only ever cancelled by genuine server shutdown (`signals.CancelOnShutdown`, `server.go:343`) — there is no watch/retry loop that clears it on its own (see point 4) — so `validateCRDSchemas` returns `s.ctx.Err()` (`context.Canceled`) at that point, not `nil`. `run()`'s existing `if err := s.validateCRDSchemas(); err != nil { return err }` then bails out immediately instead of falling through to `checkNodeAgent()`, `initRepoManager()`, `setupBeforeControllerRun()`, and `runControllers()` (`server.go:362-374`) during shutdown — and `cmd.CheckError` (`pkg/cmd/errors.go`) already special-cases `context.Canceled` to skip printing a scary error message while still exiting non-zero, so this reuses an existing mechanism rather than adding a new one.
3. A new `/readyz` handler is added to the metrics HTTP mux (`pkg/cmd/server/server.go`) and returns `503` while the not-ready flag is set, `200` once it's cleared. The not-ready flag starts `true` (set before the metrics server is even listening, so there's no window where the process looks ready before it actually is). **It clears once the manager's caches have actually synced, not merely once we're about to call `s.mgr.Start(s.ctx)` (`server.go:939`).** `mgr.Start` blocks for the process's entire operational lifetime (only returning at shutdown), so clearing "after `runControllers()` returns" is impossible in practice — that's "at shutdown," never "once controllers are serving." But clearing *immediately before* calling `Start` is also not quite right: `Start` is what kicks off the manager's informers, and controller-runtime's own convention for knowing when they've actually synced is `s.mgr.GetCache().WaitForCacheSync(ctx)`, which blocks until sync completes (or the context is done) — calling it before `Start` would deadlock, since nothing populates the cache until `Start` runs. The correct shape is a goroutine that calls `WaitForCacheSync` concurrently with the blocking `Start` call and only then flips the flag:
   ```go
   go func() {
       if s.mgr.GetCache().WaitForCacheSync(s.ctx) {
           notReady.Store(false)
       }
   }()
   return s.mgr.Start(s.ctx) // blocks until shutdown
   ```
   This way `/readyz` reflects an actual controller-runtime-verified signal (caches synced, controllers running) rather than "we reached the call site" — the latter would report Ready during the real, if usually brief, window while informers are still doing their initial List/Watch. **This requires relocating the metrics HTTP server's startup**, not just adding a new handler to it in place: today it's started inside `runControllers()` (`server.go:549-557`), which a `strict`-mode block never reaches, since `validateCRDSchemas()` runs *before* `runControllers()` in `run()` (see Integration point) — so `/readyz` would never actually be listening at the moment it's needed. The fix moves that `http.Server`/`ListenAndServe()` call out of `runControllers()` and earlier into `run()`, before `validateCRDSchemas()` is called — removing it from its old location so the listener starts exactly once, not twice. `pkg/install/deployment.go` gains a matching `readinessProbe` — concretely, `httpGet: {path: /readyz, port: metrics}` against the container's existing named `metrics` port (`8085`, `pkg/install/resources.go:100`, already declared on the container today for the `/metrics` endpoint), with `periodSeconds: 10` and `failureThreshold: 3` as reasonable startup-check defaults (and deliberately no `livenessProbe` here — a liveness probe pointed at anything tied to readiness would restart the very process this design keeps alive on purpose, undoing the whole point). Velero's default (non-chart) install has no `Service` in front of this pod today (metrics scraping is via a `prometheus.io/scrape` pod annotation, not a Service), so the probe's practical effect there is on `kubectl get pods`/`kubectl rollout status`/`kubectl wait --for=condition=ready` visibility, not Service endpoint removal — still real value, just not traffic-routing value. The probe only takes effect for Deployments generated by this version's `velero install`; a hand-maintained manifest won't gain it until regenerated, or until the operator adds an equivalent `readinessProbe` against `/readyz` by hand.

**Velero's Helm chart lives in a separate repository (`vmware-tanzu/helm-charts`), not this one, and needs more than "add a probe" — it already ships one, aimed the wrong way.** Its `values.yaml` defaults `livenessProbe` *and* `readinessProbe` to `httpGet: {path: /metrics, port: http-monitoring}` (rendered whenever `.Values.metrics.enabled`, the chart's default). `/metrics` is served by the same long-lived handler this design's `/readyz` sits alongside and is completely unaware of the not-ready flag, so the chart's *existing* `readinessProbe` would keep reporting `200`/Ready straight through a `strict`-mode block — worse than "no probe," since it actively masks the not-ready state chart users would most want to see. This is a follow-up for that repo, on its own release cadence, but it's a values.yaml default change (retargeting `readinessProbe` to `/readyz`), not just an addition — until it lands, chart-based installs get a false-positive Ready signal during a block, and the liveness probe's continued `/metrics`-based success is at least harmless (it was never tied to readiness, so it won't cause an unwanted restart either way). The retargeted `readinessProbe` should also render unconditionally rather than staying gated on `.Values.metrics.enabled` as it is today — pod readiness is a core-server-health concern, not a metrics/Prometheus-integration one, and an operator who disables metrics scraping shouldn't lose the not-ready signal as a side effect. There's no way for the running server to detect what probe config its own Deployment was rendered with, so this can't be enforced programmatically (e.g. refusing to honor `strict` mode until the chart is patched) — the chart-side fix should be treated as a release dependency to call out prominently in this feature's release notes/docs, not silently left for someone to discover the hard way.
4. The block is **not** self-clearing. Once the operator runs a remediation command (below) and the CRDs are fixed, they still need to restart the pod (e.g. `kubectl rollout restart deployment/velero`) for the server to re-run `validateCRDSchemas` and actually start controllers — this design does not add a watch/retry loop that detects the fix in place and resumes on its own. That's a deliberate scope call: a self-healing watch loop is a second, separable feature (polling cadence, backoff, when to give up) layered on top of "don't crash-loop," and isn't needed to fix the original problem (an un-exec-able container). Worth revisiting as a follow-up if manual restarts prove annoying in practice.

Remediation commands, logged and equally documented so the operator can choose based on their RBAC:

- **In-place:** `kubectl exec -n <ns> deploy/velero -- velero install --crds-only --apply` — runs the pod's own `/velero` binary under the pod's ServiceAccount. This works with no kubeconfig file present in the container: `pkg/client/client.go:31-33`'s `Config()` explicitly falls back to in-cluster configuration when no `--kubeconfig`/`$KUBECONFIG` is found (its own doc comment: "using either the kubeconfig (if specified) or an in-cluster configuration"; its error message names the same fallback), via `clientcmd.NewNonInteractiveDeferredLoadingClientConfig`'s standard `icc.Possible()`/in-cluster-config path — the same mechanism every kubectl-plugin-style binary relies on to work both from a local kubeconfig and from inside a pod.
- **Local CLI:** run `velero install --crds-only --apply` from the operator's own already-installed Velero CLI, pointed at the cluster via kubeconfig — needs no copying, and is the simpler option whenever a matching-or-compatible CLI is already on hand.
- **Copy-and-run, as a fallback:** `kubectl cp <ns>/<pod>:/velero ./velero && ./velero install --crds-only --apply` — only needed if no local CLI is available. Two caveats: the copied binary is Linux (matching the container's OS/arch), so it won't run natively on a macOS or Windows workstation, or on a different CPU architecture — download a platform-matched CLI release instead, or run the copied binary inside a Linux container matching the pod's arch. Separately, `kubectl cp` itself execs `tar` inside the target container to stream the file out; Velero's runtime image (`paketobuildpacks/ubuntu-noble-run-tiny`, per the repo's `Dockerfile`) is a deliberately minimal "run-tiny" image and likely doesn't ship `tar` — verify with `kubectl exec ... -- tar --version` before relying on this path, and prefer Local CLI if it's unavailable.

All three commands need `--apply`, and its absence is more dangerous than a simple failure would be: without it, `velero install` issues a `Create` against each already-installed (just outdated) CRD, and on `AlreadyExists` it only *logs* `"already exists, proceeding"` and moves on (`pkg/install/install.go:283,311-312`) — no error, exit code `0`, and the stale CRD is left completely untouched. An operator running the remediation without `--apply` sees what looks like a clean success and has no reason to suspect the CRDs weren't actually updated. `--apply` (`pkg/cmd/cli/install/install.go:107`) is what makes it update existing resources instead of silently skipping them.

Either way, follow up with `kubectl rollout restart deployment/velero` — per point 4 above, the blocked process does not notice the CRDs were fixed on its own.

These options exist because two independent, easily-conflated RBAC requirements are in play:

- `kubectl exec`/`kubectl cp` themselves need `create` on `pods/exec` in the Velero namespace, for whoever is running the command — unrelated to Velero's ServiceAccount. The local-CLI option needs neither, only ordinary cluster API access.
- Actually running `velero install --crds-only` needs `create`/`update`/`patch` on `customresourcedefinitions`. Default installs get this for free via the `cluster-admin` `ClusterRoleBinding` (`pkg/install/install.go:126`), so in-place exec works out of the box. Documented [restricted RBAC](https://github.com/velero-io/velero/blob/main/site/content/docs/main/rbac.md) deployments intentionally grant only `get` on CRDs, so in-place exec will fail there with a permissions error — the local-CLI (or copy-and-run-locally) option is the workaround, since it runs under the operator's own (typically broader) identity instead of the constrained ServiceAccount.

This is a proposed extension to the design above and is not yet reflected in the reference implementation (PR #9910); its eventual implementation needs test coverage for the readiness lifecycle specifically — metrics/health server listening before `validateCRDSchemas` runs, `/readyz` returning `503` while blocked and while `s.mgr.Start` has been called but `WaitForCacheSync` hasn't yet returned `true`, `/readyz` returning `200` once `WaitForCacheSync` succeeds and staying `200` for the rest of the manager's run, `/readyz` staying `503` (not accidentally clearing) if `WaitForCacheSync` returns `false`, `s.ctx` cancellation returning `context.Canceled` rather than `nil`, and `runControllers` never being entered while a `strict`-mode block is active — alongside the `jsonFieldNames`/`schemaPropertyNames`/`checkMissing` coverage already called out above.

## Implementation

- **Expected schema + validation logic.** New `pkg/cmd/server/crd_check.go`: `crdSchemaExpectation`, `expectedCRDSchemas()`, `jsonFieldNames()` (flattens anonymous embedded fields only when they carry no explicit json tag, matching `encoding/json` promotion rules), `schemaPropertyNames()` (fail-closed: returns an explicit "path traversable" bool distinct from "no properties at this node"), `validateCRDSchemas()`, `runCRDSchemaValidation()` (CRD-fetch errors and missing-version-schema errors now feed into the aggregated failure instead of being skipped), `checkMissing()`.
- **Server flag and config.** Add `CRDSchemaCheck *flag.Enum` to `Config` in `pkg/cmd/server/config/config.go`, default it to `flag.NewEnum("warn", "warn", "strict", "skip")` in `GetDefaultConfig`, and bind `--crd-schema-check` via `flags.Var` in `Config.BindFlags` (rejects invalid values at parse time).
- **Call site.** In `pkg/cmd/server/server.go`, call `s.validateCRDSchemas()` in `run()` right after `veleroResourcesExist()` succeeds.
- **Unit tests.** New `pkg/cmd/server/crd_check_test.go` covering `jsonFieldNames` (tags, embedding, `omitempty`/`-`), `schemaPropertyNames` (path traversal), `checkMissing` (matching/missing/extra fields), `expectedCRDSchemas` (all registered kinds produce an expectation), and `runCRDSchemaValidation` across `warn`/`strict`/`skip` against a fake apiextensions client.
- **Self-resolution (proposed, separate follow-up implementation from #9910 above — see Design > Self-resolution guidance for full rationale):** relocate the metrics HTTP server's startup from `runControllers()` to earlier in `run()`, before `validateCRDSchemas()`; add the `atomic.Bool` not-ready state and `/readyz` handler; add a matching `readinessProbe` (`httpGet: {path: /readyz, port: metrics}`) in `pkg/install/deployment.go`; make `validateCRDSchemas` return `s.ctx.Err()` rather than `nil` when unblocked by shutdown; and add the readiness-lifecycle test coverage listed at the end of that section. Separately, in the Helm chart repo (`vmware-tanzu/helm-charts`, not this repo): retarget its existing default `readinessProbe` from `/metrics` to `/readyz` — not merely adding a probe, since one is already there and currently masks the not-ready state.

Reference implementation: [PR #9910](https://github.com/velero-io/velero/pull/9910) (latest relevant commit as of this update: `1ef22a132`, threads the server's `context.Context` through `runCRDSchemaValidation` instead of `context.TODO()`; note the PR branch was rebased, so this SHA supersedes earlier ones referenced above).

## Security Considerations

The validation check itself uses the server's existing kube client config and the same CRD `get` permission Velero's server already requires for other startup validation (see the documented [restricted RBAC](https://github.com/velero-io/velero/blob/main/site/content/docs/main/rbac.md)). No new RBAC scope is introduced there, and no new data is exposed.

The self-resolution guidance adds a new unauthenticated `/readyz` endpoint on the existing metrics mux — same threat model as the existing unauthenticated `/metrics` endpoint (reports only a boolean ready/not-ready state, no data exposure). It does **not** grant Velero's ServiceAccount any new RBAC: the remediation commands it suggests may require broader permissions (e.g. CRD write access) than the ServiceAccount holds under restricted RBAC, but that permission belongs to whoever chooses to run the remediation command (their own `kubectl exec` or `kubectl cp`-and-run-locally identity), not to Velero's own ServiceAccount or container image.

## Compatibility

- The feature is on by default in `warn` mode, but `warn` mode never fails startup *over a validation finding* — a CRD mismatch is only ever logged there, asynchronously (see Design > Validation flow) — so no existing deployment's server will fail to start as a result of upgrading to a server version that includes this check. (A genuine setup failure, like the apiextensions client itself failing to construct, is a different, pre-existing category of error and still propagates immediately in either mode — see Validation flow step 2.)
- `strict` mode is opt-in and is the only mode that changes startup behavior (blocks controller startup on a real mismatch, and — per the self-resolution guidance above — no longer crashes the container while doing so).
- `skip` mode fully disables the check, matching today's behavior exactly.
- The `readinessProbe` added for self-resolution only appears on Deployments generated by this version's `velero install`; existing hand-maintained manifests keep behaving as before (no probe) until regenerated. Helm-chart-based installs are a distinct, worse case, not just an absent one: the chart (a separate repo, not updated by this PR) already ships a default `readinessProbe` aimed at `/metrics`, which will keep reporting Ready straight through a `strict`-mode block until that chart's default is retargeted at `/readyz` independently — see Design > Self-resolution guidance.

## Alternatives Considered

- **Schema hash validation.** Simpler to compute, but a hash mismatch is opaque — it doesn't say which field is missing — and is brittle to cosmetic/non-semantic differences in generated CRD YAML.
- **Admission webhook enforcement.** Would prevent an incompatible Pod from ever running, but requires webhook infrastructure and certificate management disproportionate to a startup self-check; could be revisited later if `warn`/`strict` prove insufficient.
- **Strict patch-version matching.** Raised during issue discussion as an alternative to schema diffing, but rejected because it would either force a CRD reapply on every patch release (if CRD version is always incremented) or require a separate mechanism to know which patch releases changed the schema. Schema-property comparison naturally tolerates patch releases with no schema changes.

## Open Issues

- Whether `strict` should become the default in a future major version once the check has proven reliable across the community.
- Whether the aggregated warning should also be surfaced as a Kubernetes `Event` on the Velero deployment/pod for better operator visibility, in addition to server logs.
- Follow-up design for the deferred CRD-ahead-of-server / extra-field case (see Non Goals): whether it warrants its own flag, and whether `strict` there should even be offered given nothing is actually broken, just silently ignored.
- Whether `veleroResourcesExist()`'s own missing-CRD detection (see Design > Validation flow) should be unified into this same validation-unavailable/missing-field framework, so a wholesale-missing CRD gets `strict`-mode's blocking-not-crashing treatment too, instead of the older `os.Exit(1)` crash path it triggers today. Real improvement, but bigger in scope than this design as written.
